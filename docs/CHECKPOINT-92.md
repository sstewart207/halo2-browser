# CHECKPOINT — NEWEST-92 (October 3, 2026)

**Later verification:** `CHECKPOINT-94.md` captured a fresh live page and did not reproduce the 4063/4096-byte source-page match reported below (it found 466 matching bytes). Treat that match and the proposed source page as an observation from one earlier capture, not established provenance. The live patched entry and call to `0x78fccb` were independently confirmed. `CHECKPOINT-93.md` also supersedes the build status below: Build 92 compiled and booted.

**The Build 91 stop is an intentional rewritten return into runtime code.** It is not a missing Ghidra function entry or a safe alias to `0x453210`. Live Chrome still stops at indirect target `0x1970421`; no AOT menu/video/campaign/60-fps acceptance. Build 91 and all 1,093 passing tests remain unchanged.

Ghidra decompilation of `FUN_00422ec1` (private `../halo2-browser/scratch/ghidra/decompile_422ec1.txt`) proves the mechanism. The hook reads its caller's saved continuation from `*(param_1+4)`, allocates an RWX page with `VirtualAlloc`, copies 0x400 dwords (4096 bytes) from an EXE page, relocates and transforms parts of the copy, inserts a `CALL` to a profiling hook, then writes a relocated destination back to `*(param_1+4)`. Thus the guest hook intentionally changes the next `RET` destination. The companion hook at `0x78fccb` calls compiled `FUN_00423b32`, which appears to continue the transformation; do not skip either hook.

The full 4096-byte live page at `0x1970000` was compared against the private EXE. **4063 bytes match the EXE page starting at `0x661e28`**, with differences only at page offsets `0x421..0x435` (21 bytes), `0xac3..0xac9` (7), and `0xcd8..0xcdc` (5). At offset `0x421`, the rewritten bytes start `PUSH ESI; MOV ESI,[ESP+8]; TEST ESI,ESI; CALL 0x78fccb`. The first seven bytes happen also to match EXE `0x453210`; NEWEST-91 mistook that short match for the page's source. The full-page match establishes the actual copied source. Address `0x1970421` corresponds by page offset to source `0x662249`, but that source address is in the middle of `FUN_00662215` and its bytes differ at the patch. **Dispatching to that static function would execute different code.**

Next implementation boundary: decode the reachable patched x86 bytes in the browser, execute them with the live guest memory/register/flag state, and transfer to the compiled profiling hook. The existing AOT bridge already has shared guest memory plus ESP and most GPR globals; EAX/ECX are call arguments, while condition flags are mainly function locals and need explicit boundary transfer. Ghidra's companion function `FUN_00423b32`, reached from hook `0x78fccb`, reads the saved flags and return slot to choose its next branch, so flag transfer is required. A blind v86 fallback is not immediately available because the v86 CPU is stopped before its protected-mode bootloader runs.

The official [iced-x86 JS/WASM decoder](https://github.com/icedland/iced/blob/master/src/rust/iced-x86-js/README.md) was installed only in a private scratch directory for a focused spike. It decoded the observed prefix exactly as `PUSH ESI` at `0x1970421`, `MOV ESI,[ESP+8]` at `0x1970422`, `TEST ESI,ESI` at `0x1970426`, and `CALL 0x78fccb` at `0x1970428`. This proves browser-capable decoding is available; it does **not** execute code or solve state transfer. No decoder dependency was added to the repository. First prove a decoded prefix and faithful hook transition in a synthetic test, then run Chrome and inspect the next return rewrite.
