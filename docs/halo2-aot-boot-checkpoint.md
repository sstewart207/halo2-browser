# NEWEST-41: Chrome AOT boot verified; native CRT exits before rendering

Oct 2, Codex. Desktop Chrome extension run at http://127.0.0.1:5174/?game=dev loaded private halo2-2gb.wgb. Worker logs prove AOT selection, 17,858,880-byte module compilation in 29.45 ms, 31,788 exports, security-cookie entry invocation and ___tmainCRTStartup invocation at ESP=0x1302000. GetVersionExA logs "dwSize too small: 0"; entry returns 0xff. Browser remains on STARTING HALO 2. No Vista dialog, title/menu pixels, menu navigation or 60 FPS acceptance on this AOT run. No evidence of fallback to emulation.

Leading source-supported diagnosis, not yet experimentally fixed: worker passes cpu.wasm_memory to RecompilerRunner. v86 creates guest mem8 with a nonzero allocation offset (vendor/v86/src/cpu.js create_memory), but runner DataView(memory.buffer), bridge Uint8Array(memory.buffer), and lifted loads/stores address raw WASM memory starting at zero. Existing guest-aware host readers account for mem.byteOffset. The Windows API may therefore read a different physical location from the AOT store. CRT CFG sets [ESI]=0x94 immediately before GetVersionExA; observed size zero is consistent with this mismatch. Next: measure live guest byteOffset and verify the written struct in both views; then implement one coherent guest-address translation for compiled memory access and host bridge. Do not merely change the host view while leaving compiled loads/stores at zero, and do not copy guest RAM into overlapping raw offsets. Reuse actual scheduler TEB/TLS rather than confusing fixed 0x30000 with initialized main-thread TEB 0x1302000. Loaded native DLL initialization/calls also need explicit AOT coverage before claiming full boot.

Validation this turn: TypeScript clean, four focused calling-convention/global/runner tests pass (19 assertions). Runner test is synthetic and uses zero-offset memory; it does not test this real shared-memory layout. No source changes made.
